# ADR 0011：默认工具链升级到 Rust 1.97.1，MSRV 保持 1.88

Status: Accepted
Last updated: 2026-07-31
## Context

ADR 0007 把仓库默认工具链和最低支持版本同时固定在 Rust 1.88。这个起点让
Phase 0 spike 可重复，但固定版本不会自动获得 Cargo、rustc 或 LLVM 修复。

2026 年出现了足以触发升级评审的具体证据：

- [CVE-2026-33056](https://blog.rust-lang.org/2026/03/21/cve-2026-33056/)
  涉及 Cargo 解包第三方 registry crate，Rust 1.94.1 更新了受影响依赖；
- [CVE-2026-5222](https://blog.rust-lang.org/2026/05/25/cve-2026-5222/)
  影响 Rust 1.68 至 1.96 所带 Cargo 的 sparse registry credential
  normalization；
- [CVE-2026-5223](https://blog.rust-lang.org/2026/05/25/cve-2026-5223/)
  影响 Rust 1.96 以前所有 Cargo 的第三方 registry symlink 解包；
- [Rust 1.97.1](https://blog.rust-lang.org/2026/07/16/Rust-1.97.1/)
  修复一个至少从 Rust 1.87 起存在的 LLVM optimization miscompilation。

前两个 Cargo 风险需要特定第三方 registry 条件，crates.io 有服务端限制；它们
不能单独证明当前锁文件已被利用。LLVM 错误编译则直接影响以 1.88 生成发布物的
正确性假设。继续把 1.88 用作默认/发布编译器不再是合理的保守选择。

另一方面，当前依赖仍能以 1.88 构建，升级默认工具链不要求同时破坏 MSRV 契约。
“用什么版本发布”与“允许调用方最低使用什么版本”必须分开。

## Decision

- 根 `rust-toolchain.toml` 固定 channel `1.97.1`，继续使用 `minimal` profile
  以及 `rustfmt`、`clippy` components。
- 所有 spike 的 `package.rust-version` 保持 `1.88`；Phase 1 workspace 继续从
  `[workspace.package]` 声明 MSRV 1.88。
- 默认开发、Clippy、测试、release 和正式 staticlib 使用固定 1.97.1。
- MSRV job 显式使用 `cargo +1.88.0`，只在 locked、可信 registry 或离线/隔离
  条件下验证兼容性，不把旧 Cargo 用作日常依赖获取工具。
- 历史 Phase 0 runner 中显式的 `+1.88.0` 和 `rust:1.88.0-*` 保留，用于逐字节
  复现旧实验；新开发命令使用根工具链或显式 `+1.97.1`。
- CI 最少包含固定 default 1.97.1 与固定 MSRV 1.88 两条 job；浮动 `stable`
  可以作为前瞻信号，但不能替代可重复的发布版本。

升级默认工具链不授权更新 Cargo dependencies。lockfile、feature 和 crate
版本在本决策中保持不变。

## Validation evidence

[`rust-toolchain-upgrade-1.97.1.md`](../../research/rust-toolchain-upgrade-1.97.1.md)
记录固定 Windows/Linux 实验，机器摘要位于
[`rust-toolchain-upgrade-1.97.1.json`](../../research/data/rust-toolchain-upgrade-1.97.1.json)。

已验证：

- 五个独立 spike 在 1.97.1 下通过 rustfmt、Clippy 和 unit/doc tests；
- 1.97.1 新增的五条 signature-parser Clippy diagnostic 已以不改变行为的方式
  修复，并在 1.88 与 1.97.1 下通过同一 14-test suite；
- `c-static-link` 与 `rquickjs-static-link` 均通过 Linux GNU、Windows `/MD`、
  Windows `+crt-static`/`/MT` C consumer；
- Linux 使用固定 `rust:1.97.1-slim-bookworm@sha256:99e09cb...`，断网、只读
  源码和只读 Cargo registry cache；
- native system library 集合未相对 1.88 基线增加。

## Alternatives considered

### 保持默认 1.88，只升级本机 Cargo

rustup 工具链中的 Cargo、rustc、LLVM 和标准库是一个经过发布测试的整体。单独
替换 Cargo 不能修复 rustc/LLVM 错误编译，还会制造非官方组合。

结论：拒绝。

### 默认固定 1.96.1

可以覆盖本轮 Cargo 安全修复，但不包含 Rust 1.97.1 对 LLVM miscompilation 的
修复。

结论：拒绝。

### 同时把 MSRV 提升到 1.97.1

没有依赖、语言能力或平台支持证据要求提高调用方最低版本；双版本验证证明当前
代码仍支持 1.88。无理由提高 MSRV 会减少可用平台，而不增加发布安全性。

结论：拒绝。

### 使用浮动 `stable`

能自动得到修复，但无法固定 rustfmt、Clippy、native-static-libs 和产物基线，
不满足可重复发布要求。

结论：不作为默认或发布工具链。

## Consequences

正面：

- 默认构建避开已知 Cargo 问题和 1.87 起的 LLVM 错误编译；
- 默认/发布版本可重复，不随 `stable` 漂移；
- MSRV 不被无关地提高；
- CI 可以分别证明发布正确性与最低版本兼容性。

代价：

- 开发环境和 CI 需要同时保存 1.97.1 与 1.88；
- 新 Clippy 可能要求不改变行为的维护性修正；
- 每次默认工具链升级都必须重跑 native static-link 与差分门禁；
- MSRV job 仍运行旧 Cargo，必须限制 registry 和网络暴露。

## Security boundary

升级 Cargo 不会使第三方 crate 自动可信。Cargo build script 和 proc macro 本来
就能在构建时执行代码；lockfile、checksum、许可证、来源审计、隔离与最小网络
权限仍是独立门禁。

## Decision acceptance

Phase 0 评审确认以下决策方向：

- 默认 Rust 1.97.1、MSRV 1.88；
- 本机双工具链验证已通过 fmt/Clippy/test 和六条 native C consumer 路径。

评审结论：决策方向 Accepted，实现期门禁如下。

## Implementation exit

以下条件在 Phase 1+ 满足后才能视为完整交付：

- 裸 `rustc`、`cargo`、`rustfmt` 和 `clippy` 精确解析到 1.97.1；
- 全部 spike 的 1.97.1 fmt/Clippy/test 通过；
- 受本变更修改的 Rust source 在 MSRV 1.88 下 fmt/Clippy/test 通过；
- 六条 native C consumer 路径继续成功；
- 完整 Python policy/report tests 和 `verify_upstream.py` 通过；
- Phase 1 CI 显式建立 default 与 MSRV job。
