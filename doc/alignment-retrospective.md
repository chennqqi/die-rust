# 对齐方法论深刻反思：为什么对齐了很多次仍有大量差异

**日期**：2026-08-23
**范围**：Phase 0-16 全历程回顾，聚焦"为什么反复对齐仍无法消除差异"

## 一、现状

经过 Phase 0-16 的持续对齐工作（14 轮 host API 语义修复、6 轮方法论重建），
当前差分测试结果：

| 语料 | 样本数 | 检测一致率 | 剩余差异 |
|------|--------|-----------|---------|
| pe_malicious | 500 | 93.8% | 31 |
| pe_benign | 100 | 93.0% | 7 |

从 80.8%/64.0% 提升到 93.8%/93.0%，但 **38 个差异仍无法消除**。

## 二、根因分析：为什么反复对齐仍有差异

### 根因 1：覆盖率审计验证"存在性"，不验证"语义正确性"

**表现**：Phase 15 声称 host API 覆盖率 100%（155 个方法全部可调用），但真实
数据差分立即暴露 14 个语义错误。

**深层原因**：覆盖率审计的工具（`audit_host_api.py`）只检查"方法名存在且可调用"，
不检查"参数签名、返回值类型、边界行为与上游一致"。一个方法可以存在、可调用、
返回正确类型的值，但**语义完全错误**。

**典型案例**：
- `getAddressOfEntryPoint`：返回 RVA 而非虚拟地址（ImageBase + RVA）
- `cleanString`：no-op 而非过滤控制字符
- `getResourceNameOffset`：找不到时返回 0 而非 -1
- `isImportPositionHashPresent`：用 FNV-1a 而非 CRC32C
- `read_uint32`：返回 i32 而非 f64（u32 比较溢出）

**为什么反复对齐没发现**：每次对齐都只验证"方法存在"，从未用真实样本验证
"返回值与上游一致"。覆盖率 100% 制造了"已完成"的错觉。

### 根因 2：签名语法理解错误，且错误被测试"确认"

**表现**：`$` 签名标记被当作通配符处理，影响 424 个 PE 规则。修复后检测一致率
从 81.8% 飙升到 93.6%。

**深层原因**：DIE 的签名语法有 7 种特殊标记（`$`/`#`/`%`/`!`/`_`/`+`/`*`），
每种都有复杂语义。开发者从签名外观推断语义（`$` 看起来像通配符），而非阅读
上游 `getSignatureRecords` 的源码。**错误的理解被写入了测试期望值**，使测试
"通过"但实际错误。

**典型案例**：
- `$` = 相对偏移跳转（不是通配符）
- `$$$$$$$$` = 读取 4 字节有符号整数，计算跳转目标 RVA，转换回文件偏移
- 跳转后继续在目标位置匹配剩余签名

**为什么反复对齐没发现**：签名解析是底层基础设施，所有 `compareEP`/`compare`
调用都依赖它。错误被"分布式"隐藏在 424 个规则中，单个规则的失败看起来像
"这个规则不匹配"，而非"签名解析器有 bug"。

### 根因 3：上游隐式行为未文档化，只能通过源码考古发现

**表现**：Unknown 占位检测占 39 个差异（pe_malicious 中最大的单一差异源）。
上游引擎在无检测时自动添加 "Unknown" 记录，但这个行为没有在任何 help 文档
或 API 说明中提及。

**深层原因**：DIE-engine 是一个 C++/Qt 项目，其行为定义在 `XScanEngine` 的
C++ 源码中，而非任何规格说明。以下隐式行为只能通过阅读源码发现：

- `XScanEngine::_processDetect` 中的 `bAddUnknown` 逻辑
- `XBinary::cleanString` 只保留字母/数字/标点
- `XPE::_getEntryPointAddress` 返回 ImageBase + RVA
- `XBinary::compareEntryPoint` 的 RVA→offset 转换
- `getSignatureRecords` 中 `$`/`#`/`%` 的解析逻辑
- `_runtime_helpers` 中的 `String.prototype.append` 定义

**为什么反复对齐没发现**：对齐工作依赖"help 文档 + _init 脚本"作为参照，
但这些只覆盖了**显式 API**。隐式行为（控制流、数据转换、边界处理）只能通过
C++ 源码考古发现，而源码考古没有系统性进行。

### 根因 4：测试用合成样本，合成样本不触发边界条件

**表现**：Phase 14 的 `corpus_differential.rs` 使用 `minimal.exe`（EP=0、无段）
等合成样本。这些样本设计为"最小可解析"，不包含真实 PE 文件的复杂性。

**深层原因**：合成样本验证"不崩溃"和"基本检测"，但不验证"与上游行为一致"。
真实 PE 文件有：
- 非标准段对齐（RVA ≠ file offset）
- 多层嵌套资源目录
- 控制字符嵌入版本字符串
- ImageBase + EP = 0 的边界情况
- .NET 元数据与 PE 头的交互
- 签名跳转目标跨段

**典型案例**：
- `cleanString` bug：合成样本的版本字符串不含控制字符，所以 no-op 实现通过了测试
- `getAddressOfEntryPoint` bug：合成样本 EP=0 且 ImageBase=0，所以 RVA=VA=0
- `$` 跳转 bug：合成样本的 EP 字节不含 call 指令，所以通配符处理通过了测试

**为什么反复对齐没发现**：合成样本是"自证"的 — 开发者设计样本、设计期望值、
设计测试，三者循环引用，错误无法被发现。

### 根因 5：过度检测与漏检的根因不同，需要不同的发现策略

**表现**：剩余 38 个差异中，13 个是过度检测（diec-rust 多检），5 个是漏检
（diec-rust 少检），13 个是双向差异（版本/格式不一致）。

**深层原因**：
- **过度检测**：diec-rust 的条件判断比上游"宽松"（返回值语义错误导致条件
  误触发）。需要"负向差分"（上游不检测、diec-rust 检测）才能发现。
- **漏检**：diec-rust 的条件判断比上游"严格"（缺少隐式行为或语义错误）。
  需要"正向差分"（上游检测、diec-rust 不检测）才能发现。
- **版本差异**：检测到了但版本/格式不一致。需要"值差分"（比较版本字符串）
  才能发现。

**为什么反复对齐没发现**：Phase 15 的差分框架只做"检测名匹配"，不做"版本值
匹配"和"负向断言"。三个维度的差异需要三种不同的发现策略。

### 根因 6：上游规则本身的 bug 导致"正确实现"产生"错误结果"

**表现**：`archive_Resources.6.sg` 的循环条件 `!bDetected` 在 `bDetected=true`
时立即退出，导致只要 EP==0 就检测到 Resources，不管有无可执行段。这是规则
本身的 bug。

**深层原因**：上游规则不是完美的 — 它们有自己的 bug、隐式依赖、和未文档化
的假设。当 diec-rust 正确实现了 host API，但规则本身有 bug 时，"正确实现"
反而产生"与上游不一致"的结果。

**典型案例**：
- `archive_Resources.6.sg`：循环条件 bug（但上游的 `getAddressOfEntryPoint`
  返回非 0 值掩盖了这个 bug）
- 上游 `isNET` 未定义导致 5 个规则抛异常（但上游仍然输出结果，异常被静默忽略）

**为什么反复对齐没发现**：对齐的目标是"与上游输出一致"，而非"正确"。
当上游规则有 bug 时，diec-rust 需要复制 bug 才能一致，这与"正确实现"矛盾。

### 根因 7：对齐是 O(n) 问题，但验证是 O(n×m) 问题

**表现**：155 个 host API 方法 × 1186 个规则 × 数百个样本 = 数万次交互。
每次交互都可能暴露一个不同的语义错误。

**深层原因**：对齐工作的时间复杂度是：
- 实现 155 个方法：O(n)
- 验证 155 个方法的语义正确性：需要 × 1186 个规则 × 数百个样本 = O(n×m×k)

Phase 15 只做了 O(n) 的存在性验证，没有做 O(n×m×k) 的语义验证。Phase 16
通过真实数据差分做了 O(m×k) 的验证，但每次只发现 1-3 个语义错误，需要
多轮迭代才能收敛。

**为什么反复对齐没发现**：每轮对齐只发现"当前样本集触发的"语义错误。
不同样本集触发不同的错误，需要持续差分才能逐步收敛。

## 四、方法论改进建议

### 建议 1：建立"语义对照矩阵"而非"存在性矩阵"

当前 host API 审计只记录"方法存在 ✅"。应改为记录：
- 方法名
- 参数签名（与上游对比）
- 返回值类型（与上游对比）
- 返回值语义（与上游对比，用真实样本验证）
- 边界行为（找不到/越界/空输入时的返回值）

### 建议 2：持续差分，而非一次性差分

每轮修复后立即运行差分，发现新差异后立即修复。差分不是"验收工具"，
而是"开发工具"。当前 Phase 16 已经这样做了，但 Phase 0-15 都是"先实现再验收"，
导致问题积累。

### 建议 3：源码考古作为对齐的基础

对每个 host API 方法，阅读上游 C++ 源码的实现，而非仅依赖 help 文档。
help 文档只描述"做什么"，源码才描述"怎么做"。特别是：
- 返回值计算方式（如 `getAddressOfEntryPoint = ImageBase + RVA`）
- 边界条件处理（如 `getResourceNameOffset` 找不到时返回 -1）
- 数据转换逻辑（如 `cleanString` 的字符过滤规则）

### 建议 4：签名解析器需要独立测试套件

签名解析是底层基础设施，影响所有规则。应有独立的测试套件验证每种签名标记：
- `$` 相对偏移跳转（1/2/4/8 字节）
- `#` 地址解析
- `%` ANSI 字符串匹配
- `*` 非空字节
- `+` delta 搜索
- `.`/`?` 通配符
- `'string'` 字面量

### 建议 5：区分"正确"与"一致"

当上游规则有 bug 时（如 `archive_Resources.6.sg` 的循环条件），
diec-rust 需要决定：
- 复制 bug 以保持一致（短期目标）
- 修复 bug 并记录偏离（长期目标）

当前策略是"一致优先"，但应记录已知的上游 bug，避免被误认为是 diec-rust 的缺陷。

### 建议 6：扩大差分样本规模和多样性

当前 500+100 样本只覆盖了 PE 的部分场景。应扩展到：
- 更多 ELF 样本（当前 elf_malicious 一致率仅 24%）
- 更多 .NET 样本（.NET protector 漏检较多）
- 更多 Delphi/Embarcadero 样本（版本推断差异集中）
- 更多带签名的样本（Authenticode 过度检测）

## 五、结论

反复对齐仍有差异的根本原因是：**对齐验证的维度不够**。

- Phase 0-14 验证"能加载" → 不等于"能检测"
- Phase 15 验证"方法存在" → 不等于"语义正确"
- Phase 16 验证"检测结果一致" → 但只用了 600 个样本

每个层面的验证都会发现前一层面的遗漏，形成"修复→验证→发现新问题→修复"
的迭代循环。这个循环不会终止，因为：

1. 上游有 155 个方法 × 复杂语义 × 隐式行为 = 几乎无限的组合空间
2. 上游规则本身有 bug 和隐式依赖
3. 真实样本的多样性远超合成测试

**收敛策略**：持续差分 + 源码考古 + 语义对照矩阵。不追求"100% 一致"，
而是"每次差分都比上次更好"，并在文档中记录已知差异和上游 bug。
